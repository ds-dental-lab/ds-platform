**2026-08-11 확정** (설계서 §2.1 C-4 를 A안으로).

| | 사양 수정 | 파일 수정 | 삭제 |
|---|---|---|---|
| 접수 | O | O | O |
| 재스캔 | **X** | O | O |
| 디자인 이후 | X | X | X |

**Why — 재스캔에서 사양을 막는 이유 (사용자 설명):**
재스캔은 디자인센터가 "스캔이 이상하니 다시 찍어 달라"고 부른 상태입니다.
문제가 된 건 파일이지 사양이 아닙니다. 여기서 사양까지 열어 두면 —

```
치과: 16번 지르코니아 + 스캔 업로드
디자인센터: 스캔이 흐리네요 → 재스캔 요청
치과: 스캔 다시 올리면서 17번 추가, 재료도 PMMA 로 변경
디자인센터: 자기가 요청한 것(파일)만 바뀐 줄 알고 그대로 제작
```

**주문 취소 버튼은 없앴습니다.** 치과가 그만두는 길은 삭제 하나로 모았습니다 —
같은 자리에서 같은 사람이 누르는 버튼이 둘이면 무엇이 다른지 알 수 없습니다.
`canCancel` 과 `cancelled` 상태는 남아 있습니다 (화면에서만 내림).

**How to apply:**
- `editScopeOf(status)` → `'full' | 'files' | 'none'`, `canEditSpec`, `canDeleteOrder`
- 세 겹으로 막습니다 — 버튼 / `/edit` 라우트 리다이렉트 / `updateOrder` 서버 검사
- 재스캔의 전진 버튼은 `getAvailableActions` 에서 뺐습니다.
  파일 재등록 화면(`RescanBar`)이 파일과 상태를 한 동작으로 처리합니다.
- 리메이크를 지우면 원주문의 `remake_count` 를 **다시 세어** 덮고,
  0이면 리메이크 이슈를 해소합니다 (빼지 않고 다시 셉니다).

## ★ 디자인센터는 단계를 안 가립니다 (2026-08-12 재결정)

*"디자인계정 및 디자이너는 모든 단계에서 주문수정 및 주문삭제가 가능해야한다"*

위 규칙(접수·재스캔까지)은 **치과에만** 남습니다. 디자인센터는 **완료된
주문까지** 고치고 지웁니다.

**왜 뒤집었나** — 원래 이유가 "이미 남이 그 사양으로 일을 시작했으니까"
였는데, **그 일을 하는 쪽이 디자인센터 자신**입니다. 전화로 "이거
바꿔 주세요" 를 받아 처리하는 곳이기도 합니다.

★ 디자인센터에는 **수정 화면이 아예 없었습니다.** 새로 만들었습니다
  (`/design/orders/[orderId]/edit`). 주문의 주인은 그 치과이므로
  **치과 이름과 그 치과의 즐겨찾기**를 씁니다.

### 안전장치는 이미 있었습니다 (확인함)

| | |
|---|---|
| 청구서 | `billing_lines.order_id` 가 **RESTRICT** — 청구서에 실린 주문은 DB가 하드 삭제를 거부합니다 |
| 의뢰서 2년 보존 | `soft_deleted` 파기는 **파일만** 지웁니다. 주문 줄은 안 지워집니다 |
| 리메이크 | 지우면 원주문 횟수를 다시 세어 덮고, 남은 게 없으면 이슈도 내립니다 |

### 대신 지우기 전에 알려 줍니다 (`deleteWarnings`)

막지 않기로 했으면 알려 줘야 합니다. 접수 건과 완료 건은 결과가 전혀
다른데 같은 창을 띄우면 그 차이를 모른 채 누릅니다.

- 완료·취소 → 통계에서 빠짐 · 마감 전이면 청구액이 줄어듦
- 전부 공통 → 치과 화면에서도 사라짐 · **화면에서 되돌릴 수 없음**

★ **되살리는 화면이 없습니다.** `deleted_at` 만 찍히므로 데이터는 살아
  있지만 화면에서 복원할 길이 없습니다. 필요해지면 그때 만듭니다.

★ **통계는 소급해서 바뀝니다.** 지운 주문은 `deleted_at is null` 필터에
  걸려 빠지므로 지난달 리메이크율이 오늘 달라집니다. 디자이너 평가에
  쓸 거면 월 마감 시점의 통계를 굳혀 두는 일이 따로 필요합니다.
