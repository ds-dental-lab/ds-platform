## 파일 — 올리기 전에 줄을 만듭니다

`order_files.upload_status` = `pending` → `uploaded` / `failed`.
끝난 뒤에 만들면 **끊긴 파일은 이름조차 안 남습니다.**
남아 있는 pending 줄이 곧 "이 파일이 빠졌다" 는 증거라 **지우지 않습니다**.

- `File Count (n/m)` — m = 전체 줄(보낸 수), n = uploaded 줄(도착한 수).
  같은 걸 두 곳에서 세면 어긋납니다 — 줄로만 셉니다
- 어긋나면 **빠진 파일만 다시 올립니다.** 이름으로 짝을 맞추고, 저장소 경로는
  새로 뽑습니다(끊긴 자리에 덩어리가 반쯤 남아 있을 수 있음).
  주문을 지우고 새로 넣으면 치식·쉐이드·시한이 다 다시 가고 대화·이력이 끊깁니다
- **올리는 동안 화면을 덮어 막습니다.** 글자 경고는 급한 사람이 안 읽습니다.
  클릭은 덮개가, 뒤로가기는 popstate 되돌리기가, 새로고침은 beforeunload 가
- **끊기면 스스로 2번 더** (1초·2초). 4xx 는 바로 접습니다
- 진행률은 XHR 로 얻습니다 — `supabase-js` 의 upload() 는 fetch 라 못 줍니다
- 파일 이름은 **가운데를 접습니다**(`middleEllipsis`, 28자).
  끝을 자르면 `김지영2026-08-11_15-47-06.dxd` 두 개가 똑같아 보입니다
- 목록은 168px 안에서 굴립니다 (열다섯 개까지 들어옴)
- 지우기는 **올린 쪽**이 (스캔=치과+디자인센터, 디자인=디자인센터만).
  저장소를 먼저 비우고 표를 지웁니다 — 순서가 반대면 경로를 잃습니다

## 상태 전이

- **기공소가 디자인 파일을 받으면 곧 '제작'** 입니다. 받았다는 게 시작했다는
  신호입니다. 버튼을 따로 두면 아무도 안 누릅니다.
  스캔 파일은 해당 없음. 못 넘어가도 내려받기는 성공
- **제작대기·제작 → 디자인** 되돌리기 (디자인센터만).
  기공소가 "이 디자인으론 못 만든다" 할 때. **사유는 안 묻습니다**
  (2026-08-12) — 이미 대화로 말한 뒤에 누르는 버튼이라.
  `order_status_history` 에는 그대로 남습니다.
  사유는 **재스캔·취소에만**
- 디자인 단계 버튼 이름은 **'제작주문'** — 무엇이 끝났는지가 아니라
  무엇이 시작되는지를 알아야 손이 멈춥니다.
  디자인 파일 1개 + 기공소가 있어야 넘어갑니다
- 기공소는 주문상세 아래 **셀렉박스**로 미리 정합니다 (기본값 자사 기공).
  제작대기로 넘어가면 잠깁니다

# 2026-08-20 — 업로드를 크게 손봤습니다 (작업지시서 §3)

실제 트래픽: **하루 30건, 건당 150MB.** 구성이 제각각입니다 —
150MB 한 덩어리 / 50MB 셋 / 10MB 열.

| | |
|---|---|
| 파일 하나 | 100 → **500MB** (코드·버킷·프로젝트 상한 셋 다) |
| 주문 총량 | **1GB** — 폴더째 끌어다 놓는 사고를 막습니다 |
| 6MB 초과 | **이어올리기(TUS)** — 끊겨도 그 자리부터 |
| 동시 | **3개** |

★ 총량은 **버킷에 못 겁니다** — 저장소는 파일 하나씩만 봅니다.
  화면(`checkUploadBatch`)이 봅니다. **이미 고른 것까지 합쳐서** 재야
  합니다. 안 그러면 300MB 를 세 번 나눠 고르는 식으로 지나갑니다.

## 이어올리기는 직접 짰습니다 (`lib/upload-resumable.ts`)

tus-js-client(30KB)를 안 넣었습니다. 쓰는 것이 만들기·이어붙이기·
물어보기 셋뿐이고, 진행률을 보여 주려면 어차피 XHR 을 직접 잡아야 합니다.

★ **조각은 6MB 의 배수.** Supabase 문서의 "6MB 로 두고 바꾸지 말라"
  는 말은 **하한**(S3 조각 최소치)이지 못 박은 값이 아니었습니다.
  2026-08-21 에 **24MB** 로 키웠습니다 — 아래 실측 참고.
★ 만든 자리를 localStorage 에 적어 둡니다. 창을 닫았다 열어도 같은
  파일을 다시 고르면 그 자리부터 이어집니다.
★ 실측 — 150MB 를 6MB 씩 25조각, **13.5초**. 중간에 끊고 물어보니
  6291456 바이트까지 올라가 있었고 거기서 이어졌습니다.

## ★★ 실패하면 **이유를 말해야 합니다**

`.dxd` 셋이 실패했는데 화면에는 "못 올린 파일: a, b, c" 만 떴습니다.
**서버가 뭐라고 했는지 아무도 몰라** 원인을 찾는 데 한참 걸렸습니다.
지금은 파일마다 이유가 붙습니다 — `413`, 끊긴 지점(%), 서버 응답.

## 진행률 모양이 바뀌었습니다

동시에 셋이 올라가므로 '지금 이 파일' 하나로는 못 그립니다.
`UploadProgress.active[]` 목록 + 전체는 바이트로 셉니다.


## 업로드 속도를 올린 것 (2026-08-21)

사장님 요청: "업로드 속도를 올리고 싶다."

**운영 저장소에 진짜 파일로 재 봤습니다** (150MB, 회선 ~130Mbps):

| 조각 | 왕복 | 걸린 시간 |
|---|---|---|
| 6MB | 25회 | 15.4초 |
| **24MB** | **7회** | **10.2초** ← 정한 값 |
| 36MB | 5회 | 10.0초 (더 키워도 안 빨라짐) |
| 10MB(배수 아님) | 15회 | 14.0초 (되긴 됨) |

작은 파일 여럿(10MB × 10개)은 동시 개수 문제였습니다:
동시 1개 7.1초 · 3개 4.2초 · **4개(정한 값)** · 5개 3.5초 · 8개 3.3초.

★ 5가 제일 빨랐지만 **4**로 뒀습니다. 치과 회선은 올리는 쪽이 얇아
  숫자를 늘려도 총량이 안 늘고, 끊길 때 여러 개가 한꺼번에 넘어집니다.

★ 조각을 무한정 못 키우는 이유 — 끊기면 **그 조각을 통째로** 다시
  보냅니다. 24MB 면 최악이 24MB 재전송입니다.

★ 시험은 `MAX_ORDER_TOTAL_BYTES` 같은 숫자를 못 박지 않고 **규칙**을
  못 박습니다: "6MB 의 배수" · "이어올리기 문턱보다 작지 않을 것".
  다음에 또 손댈 값이라, 숫자를 적어 두면 시험이 '바꾸지 말라' 는
  말밖에 못 합니다.

## ★★ 주문**수정**에서는 파일이 아예 안 올라갔습니다 (2026-08-21)

사장님이 찾았습니다 — "디자인 단계에서 디자이너가 주문수정으로 추가
파일 업로드시 업로드가 안 되는 현상."

`NewOrderForm` 의 수정 갈래가 `submitUpdateOrder` 만 부르고 **그대로
주문상세로 나가 버렸습니다.** 고른 파일은 들고만 있다가 화면과 함께
사라졌습니다. **오류가 하나도 안 났습니다** — 그래서 더 나빴습니다.
올린 줄 알고 나갔는데 파일이 없는 것이니까요.

★ 등록과 수정이 이제 **같은 함수**(`sendPendingFiles`)를 씁니다.
  두 군데에 따로 적으면 언젠가 한쪽만 고칩니다 — 실제로 한쪽에는
  아예 없었습니다.

★ 디자인센터 계정이 남의 주문 스캔칸에 파일을 더 넣는 것은 정책이
  막지 않습니다. 진짜 계정으로 확인했습니다 (줄 만들기 201 →
  저장소 200 → uploaded 204 → 목록에 보임).

이미 올라간 파일이 하나도 안 보여서 "안 올라갔나" 하고 같은 스캔을

★ 여기서 **지우지는 못합니다.** 지우기 규칙(누가·언제)은 주문상세의

## '업로드중' 주문 상태 (2026-08-21, 작업지시서 §3-3)

10개 중 8개만 올라간 주문이 '접수' 로 서면 디자인센터가 정상으로 보고
작업을 시작합니다. 빠진 둘이 무엇이었는지는 아무도 모릅니다.

**어떻게 도나**
- 주문등록 때 올릴 파일이 하나라도 있으면 **`uploading` 으로 태어납니다**
  (`plannedFileCount`). 이 수를 어디 적어 두지는 않습니다.
- 매니페스트는 **올리기 전에 만들어 두는 `order_files` 줄**입니다.
  이름·크기가 거기 있습니다. (옛 `orders.scan_file_expected` 칸은
  만든 **다음 마이그레이션이 걷어냈습니다** — 개수만으로는 '무엇이'
  빠졌는지 모르니까요. 그 칸을 읽던 `note_planned_scan_files` 는
  반년째 부르면 터지는 함수였고, 지금 치웠습니다.)
- **마지막 파일이 자리를 잡으면 DB 가 스스로 접수로 옮깁니다**
  (`advance_when_files_landed` 트리거). 조건: 스캔칸에 pending·failed 가
  하나도 없고, uploaded 가 하나 이상.
- ★ **사람이 미는 길이 없습니다.** 세 섹터 다 버튼 없음, `canTransition`
  도 거절. 버튼을 두면 덜 올라간 채로 눌러 넘길 수 있습니다.
- ★ 실패가 남으면 머무릅니다. 못 올린 줄을 **지우면** 그때 넘어갑니다
  ('그건 빼겠다' 는 뜻). 보내려 한 수와 견주지 않고 지금 남은 것으로 봅니다.
- ★ 파일을 만질 수 있는 구간에 넣었습니다 — 없으면 다시 시도도
  주문 삭제도 못 해 영영 갇힙니다.
- ★ 기공소 목록엔 안 뜹니다. 공은 치과에 있습니다(`OWNER_SECTOR`).

### ★★ 부딪힌 것 넷 — 전부 눌러 보고 알았습니다

① **열거형에 값을 더한 같은 트랜잭션에서 그 값을 못 씁니다.**
  값만 올리는 마이그레이션을 따로 둬야 합니다.

② **`orders_guard_status` 가 새 상태를 몰라 막았습니다.**
  `security definer` 여도 `auth.uid()` 는 그대로라 '트리거니까 봐준다'

  ★ 깃발(`set_config`)을 세우는 대신 **조건을 문지기가 다시 확인**하게
    했습니다. 누가 부르든 파일이 진짜 다 왔을 때만 열립니다 —

③ **`order_status_history` 의 칸은 `note` 가 아니라 `reason`.**

## 요청시한 자동 완료 (2026-10-01, 커밋 3fbf075 · migration 20261001120000)
- 사용자 요청: "제작 단계에서 배송 안 눌러도 디데이 되면 완료로".
- 대상 **production_wait·production·shipping** (접수·재스캔·디자인은 늦은 것이지 끝난 게 아님). due_date <= 오늘(KST).
  - ★ **제작대기는 2026-10-19 사용자 결정으로 추가** — 처음엔 뺐었음("아직 안 만든 것"). 기공소가 제작 단추를 안 눌러 시한이 지나도 제작대기에 남는 건이 있어서. 디데이 지나면 나간 것으로 보고 완료+shipped_at(그날) → 정산에 잡힘.
- ★★ 완료로 넘기며 **shipped_at 이 비면 지금으로 채움** — 정산은 상태가 아니라 shipped_at 으로 달을 가름(isBillable). 안 채우면 영영 청구 안 됨.
- ★ **새벽 3시 10분 KST**(cron `10 18 * * *`, 파기와 10분 차이)에 돌되, **적는 시각은 그날 한국 날짜 00:00 UTC**(stampFor) — 새벽에 돌아도 달이 안 밀림. 자정에 돌리면 한국 1일 건이 UTC 전달 말일이 되어 지난달 정산에 샘 — 테스트로 잠금(tests/domain/auto-complete).
- 밀린 건은 **오늘 날짜**로 찍힘(소급 안 함) — 이미 마감한 달에 금액이 생기는 것을 막기 위함.
- 사람 손과 충돌 방지: `.eq('status', 원래상태)` 조건부 업데이트. 이력은 order_status_history 에 actor 없이 '자동 완료'.
- 곁가지: completed_at 트리거가 같이 찍혀 **파일 400일 보관 시작일**이 당겨짐.
