**2026-08-12 결정.** *"배정된 주문서에 대해선 다른 디자이너가 디자인을
잡아서는 안되게 막아야해. 두명의 디자이너가 한 주문을 하면 안되잖아"*

`orders.designer_user_id`. 규칙은 `domain/designer` (테스트 21개).

## ★ 왜 이력으로는 안 됐나

전에는 담당자를 `order_status_history` 에서 캐냈습니다 — '디자인 단계로
옮긴 사람' 이 곧 디자이너. 읽기에는 충분했지만 **막을 수가 없었습니다.**
지나간 일을 뒤에서 읽는 값이라, 두 사람이 같은 주문을 열고 나란히 눌러도
둘 다 통과했습니다. **앞을 막으려면 사실이 표에 있어야 합니다.**

## 규칙

- **먼저 잡은 사람이 임자.** 배정 화면을 따로 안 거칩니다 — 주문마다
  배정하는 일이 하나 더 생기고, 실제로 일하는 사람이 임자가 되는 것이
  가장 덜 틀립니다
- **남이 잡은 것은 못 만집니다. 관리자도 그냥은 못 만집니다.**
  관리자만 예외를 두면 두 명이 한 주문을 만지는 일이 결국 생깁니다.
  대신 **담당을 바꾸는 길**이 있고, 누가 넘겨받았는지가 화면과 기록에
  남습니다 (한 번 더 누르는 값으로 삽니다)
- ★ **담당 이전은 디자이너끼리도 됩니다** (2026-08-12 재결정).
  처음엔 관리자만 넘길 수 있게 했는데, 일이 몰리거나 자리를 비울 때
  서로 넘기는 것은 **그날그날의 일**입니다. 그때마다 관리자를 찾게
  하면 결국 아무도 안 넘깁니다. 살아 있는 우리 조직 사람인지는
  서버가 그대로 봅니다
- **내가 잡은 것은 내가 내려놓습니다.** 안 그러면 잘못 잡은 주문이
  관리자가 자리를 비운 동안 아무도 못 건드리는 상태로 굳습니다
- **되돌아오는 것은 안 막습니다** (`needsSeat`). 기공소의 수정 요청은
  일을 뺏는 것이 아니라 **돌려주는 것**입니다. 여기까지 막으면 담당자가
  자리를 비운 사이 수정 요청이 갈 곳을 잃습니다
- 완료·취소된 건의 담당은 못 바꿉니다 — 통계가 뒤에서 흔들립니다

## ★ 막는 곳이 셋입니다

| 어디 | 무엇 |
|---|---|
| 화면 | 버튼·업로드칸을 감추고, 왜 못 하는지 **열자마자** 적습니다 |
| `changeOrderStatus` | 디자인센터 자리로 움직일 때 `checkSeat` |
| **DB** | `orders_guard_designer` 트리거 + `order_file_insert` 정책 |

서비스에서만 막으면 RLS 로 열린 update 를 타고 **자기 것으로 덮어쓸 수
있습니다.** 디자인 파일은 브라우저에서 곧장 저장소로 가므로 정책이 봐야
진짜로 막힙니다 (파일이 곧 작업입니다). 트리거는 `auth.uid()` 가 없으면
(service_role·마이그레이션) 통과시킵니다 — 그쪽은 어차피 무엇이든 합니다.

## 통계도 배정을 봅니다

이력을 그대로 뒀으면 담당을 넘겨받아 **실제로 끝낸 사람 대신 처음
눌렀던 사람에게 일량이 쌓입니다.** '언제 잡았고 언제 넘겼나' 만 이력이
답합니다.

확인 (전부 rollback): 남의 자리 뺏기 막힘 · 남의 주문에 디자인 파일 막힘 ·
내 자리 내려놓기 됨 · 빈자리 잡기 됨 · 관리자 넘기기 됨 · 담당자 파일 됨.
