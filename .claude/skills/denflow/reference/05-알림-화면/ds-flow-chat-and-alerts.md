## ★ 자사 제작 함정 (`resolveRecipients`)

디자인센터가 기공소 자리를 겸하면, **자리(슬롯)로만 가르다가 자기가 쓴
글이 자기 종에 붙습니다.** 치과가 쓴 글은 같은 조직에 두 번 갑니다.
조직 id 로 거르는 규칙을 `domain/notification` 에 순수 함수로 두고
테스트로 못박았습니다. 눈으로 읽어서는 못 잡는 자리입니다.

## ★ 신호 방식으로 만들었습니다 (2026-08-19)

"아직 케이스는 없는데 준비해두려고" — 미뤄 둔 설계 그대로 만들었습니다.
사용자가 전 직장 방식(치과는 웹 실시간 + 센터는 로켓챗 연동, 데이터는
활성 시에만)을 참고로 들었지만, **로켓챗 이중화와 '데이터 비활성화' 는
받지 않고** 연결의 수명만 가져왔습니다 — 데이터는 전부 DB, 구독만 껐다 켬.

```
글 저장(RLS) → after() 로 알림 → 신호 httpSend  ...보내는 쪽
order:{uuid} private 채널, 내용 없이 주문 id 만  ...채널
신호 수신 → router.refresh() → 서버가 RLS 로 다시 읽음  ...받는 쪽
```

- **domain/signal** — 채널 이름·이벤트·쿨다운(1초 뭉치기). 순수 함수 + 테스트
- **events/signal.ts** — `signalOrderChanged`. httpSend(웹소켓 안 엶),
  실패해도 조용 (폴링이 받쳐 줌). **알림 다음에** 쏩니다 — 먼저 쏘면
  받은 쪽 화면에 글은 붙고 종은 늦는 어긋남이 보입니다
- **OrderSignal.tsx** — 주문상세에 있는 동안만 구독. 숨은 탭은 표시만
  해 두고 돌아올 때 한 번. OrderDetailScreen 에 **AutoRefresh 도 같이**
  붙였습니다 — 신호는 빠른 길, 폴링은 반드시 오는 길. **폴링을 지우면
  안 됩니다** (Realtime 은 조용히 끊김)
- **마이그레이션 20260819120000** — realtime.messages 에 RLS.
  private 채널이라 구독·발신 모두 `can_access_order` 를 지납니다.
  익명 구독이 Unauthorized 로 거절되는 것을 운영에서 확인했습니다.
  ★ `and` 는 평가 순서 보장이 없어 **case** 로 모양 검사 → uuid 캐스팅
  순서를 못박았습니다. 화면(domain/signal)의 UUID 정규식과 같은 잣대

★ 편집·삭제도 신호를 쏩니다 (`select('id, order_id')` 로 주문 id 를
  받아서). 알림은 새 글만 만들므로 편집·삭제는 폴링에 안 잡힙니다 —
  신호가 유일한 즉시 전달 길입니다.

★ **양쪽 통과 확인은 사람 손이 필요합니다** — 두 브라우저로 치과·센터
  로그인해 같은 주문을 열고 한쪽에서 글을 보내 보기. 시험 DB 에는
  이 마이그레이션이 아직 없습니다.

`AutoRefresh` 는 자국(`actions/pulse`)만 묻고 **달라졌을 때만** refresh 합니다.
자국에 **안 읽은 알림 수**가 들어 있어야 종이 뜹니다 — 알림은 orders 를
안 건드리므로 주문만 보면 안 뜹니다. 네 섹터 화면(치과 포함) 전부에 붙었습니다.

## ★ '확인 요청' 기능은 여전히 안 만듭니다 (2026-08-13 결정 유지)

사용자가 원한 장면: *"치과에서 스캔 확인해달라고 실시간으로 온다."*
설계까지 했다가 **안 만들기로 했습니다.** 이유가 둘입니다.

1. **기능으로 만들면 모든 치과가 씁니다.** 지금은 부탁하는 곳만
   암묵적으로 해 주는 행위인데, 버튼이 생기면 인력이 감당 안 됩니다
   (사용자 지적). 해법은 있습니다 — 거래처별로 켜기(기본 꺼짐, 안 켠
   곳엔 **버튼이 아예 안 보임**) + '지금 받는 중' 스위치 + 응답시간 기록.
   설계는 이 대화에 있습니다.
2. **그런데 아직 실사용이 0입니다.** 그 통제장치는 *없는 문제*를 막는
   것입니다. 두 달 카톡으로 굴려 보면 몇 번·누가·**무엇을 묻는지**가
   공짜로 쌓입니다. 요청의 대부분이 "파일이 안 열려요" 면 답은 확인
   요청 기능이 아니라 업로드 검사입니다.

실시간이 필요해지면 **신호 방식**으로 합니다 — Realtime 채널에 주문 id
말고 아무것도 안 싣고, 받은 쪽이 우리 서버에 다시 묻습니다. 그러면
RLS 가 평소대로 막아 **새는 자리가 안 생깁니다.** AutoRefresh 를 폴링에서
신호 받기로만 바꾸면 되어 하루쯤입니다.
