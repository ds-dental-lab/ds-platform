**2026-08-13.** 사용자가 세 번 말했습니다 — *"치과 계정에서 완료처리가
된다니깐"*. 두 번은 "화면에서 뺐습니다" 라고 답했고 틀렸습니다.
DB 를 직접 찔러 보니 **정말로 되고 있었습니다.**

## 왜 화면만 보면 틀리나

서비스 계층(`changeOrderStatus` 의 `canTransition` 같은 것)은 **우리
코드를 지나갈 때만** 봅니다. 브라우저는 anon 열쇠와 자기 세션을 그대로
들고 있어서, 개발자도구에서 PostgREST 로 곧장 쏘면 그 검사를 건너뜁니다.

> **화면에서 감추는 것과 못 하는 것은 다릅니다.**

## 그날 찾은 것 다섯 (전부 고침)

| 무엇 | 마이그레이션 |
|---|---|
| 치과가 상태를 곧장 `completed` 로 (7건이 한 번에) | `20260813140000` |
| 정산 기준일·보철 재료·항목 삭제·파일 삭제 | `20260813150000` |
| **기공소가 치과 판매가 열람** (`surcharge_prices`) | `20260813160000` |
| 저장소 덩어리를 기공소가 지우기 | `20260813170000` |
| **남의 종에 가짜 알림**(바깥 링크까지) · 이벤트·열람기록 위조 | `20260813180000` |

★ **다섯 중 셋은 주석에 규칙이 적혀 있는데 코드만 빠져** 있었습니다.
  "관련된 주문이 있어야만 만들 수 있게 묶습니다" — 묶는 코드가 없었습니다.
  **주석과 정책 조건을 나란히 읽는 것**만으로 셋을 찾았습니다.

## 같은 날 더 찾은 것 둘

| 무엇 | 마이그레이션 |
|---|---|
| **입금이 적힌 청구서의 발행을 무를 수 있었습니다** — 무르면 목록에서 사라지는데 입금 줄은 남아, 받은 돈이 어느 청구서 것인지 없어집니다. 마감 안 한 기간 발행도 같이 막음 | `20260813190000` |
| **치과가 배포받은 임플란트 조합을 지울 수 있었습니다** — 화면에는 "치과가 임의로 뺄 수 없다" 고 적혀 있는데 정책에 그 조건이 없었습니다 | `20260813200000` |

## ★ 문을 좁힐 때는 그 문으로 다니던 업무를 같이 확인합니다

파일 삭제를 '접수·재스캔·디자인' 으로 좁혔더니 **보관기간 파기가 조용히
0건**이 됐습니다 — 파기가 지우는 것은 바로 그 완료된 건들입니다.
**오류도 안 납니다** (RLS 는 막을 때 0행을 돌려줍니다).
파기만 `service_role` 로 돌리게 고쳤습니다 (`actions/retention`).

그 뒤로는 공격 시험마다 **정상 경로 대조군**을 같이 넣습니다. 실제로
`record_access` RPC 가 `security definer` 가 아니라서, 조건을 잘못
걸었으면 열람 기록이 통째로 안 남을 뻔했습니다.

## 시험하는 법 (그대로 다시 쓰세요)

```sql
begin;
select set_config('request.jwt.claims',
  json_build_object('sub', <user id>, 'role','authenticated','aud','authenticated')::text, true);
set local role authenticated;
-- 공격 · 정상 경로를 한 표에 넣고 기대값과 대조
rollback;
```

★ **임시표는 `grant select to authenticated`** 를 해 줘야 읽힙니다.
★ **저장소 delete 는 SQL 로 시험이 안 됩니다.** `storage.protect_delete`
  가 먼저 막아서 '막힘' 이 정책 덕분인 줄 착각합니다. 정책의 **조건식
  함수를 자리별로 직접 불러** 확인하세요 (`can_write_order_file` 등).
★ 대조군을 잘못 고르면 거짓 양성이 납니다 — `clinic@test.kr` 이 원래
  owner 라 "역할 승격이 뚫렸다" 고 잘못 읽었습니다.

## 여덟 번째 구멍 — 값 감추려고 만든 보기가 행을 흘렸습니다 (2026-08-21)

Supabase Advisor 가 **CRITICAL** 로 잡았습니다:
`public.prosthesis_products_public is defined with the SECURITY DEFINER property`.

**무엇이 샜나.** 그 보기는 기공소에게 치과 판매가를 감추려고 만든
값 없는 목록입니다(§8.5). `security_invoker = false` 라 만든 사람
(postgres)의 권한으로 원본을 읽는데, 그 계정은 **RLS 를 통째로
건너뜁니다**(bypassrls). 게다가 보기 안에 **아무 조건이 없었습니다.**

값은 안 샜지만 **행이 샜습니다** — 로그인한 사람이면 누구나 모든
디자인센터의 제품 목록을 읽었습니다. 센터가 하나뿐이라 안 보였을 뿐,
거래처가 늘면 남의 제품 이름·약칭이 그대로 보입니다.

**왜 그냥 invoker 로 못 바꾸나.** 그러면 기공소가 아무것도 못 봅니다.
원본 표를 일부러 닫아 뒀기 때문입니다(거기 판매가가 있습니다).
★ 열은 정책으로 못 막습니다 — RLS 는 '행' 단위입니다. 그래서 값이
  빠진 보기가 필요했고, 그 보기가 원본을 읽으려면 누군가는 정책을
  넘어야 했습니다.

**고친 방법 — 넘는 자리를 보기에서 함수로 옮겼습니다.**
- `prosthesis_products_visible()` : `security definer`, 값 칸 없음,
  안에서 직접 행을 가름 (`owner_org_id = my_org_id() or is_partner_org(...)`)
- 보기는 `security_invoker = true` 로 그 함수를 읽기만 함
- 화면 코드는 **한 줄도 안 바뀜** (`.from('prosthesis_products_public')`)

★ Advisor 는 **보기**만 봅니다. security definer **함수**는 안 겁니다
  (우리 `my_org_id()` 들이 이미 다 그렇습니다). 그래서 넘는 일을
  함수 한 곳에 모으는 것이 답이 됩니다.

**진짜 계정으로 확인** (2026-08-21, 운영):
치과·센터·기공소 셋 다 값 없는 목록 8줄 ✓ / 원본 표는 기공소만 0줄 ✓ /
로그인 안 한 사람 0줄 ✓ (전에는 이 문이 없었습니다).

★ 마이그레이션은 `npm run backup` 뒤에 `npx supabase db push --linked`.
  CLI 는 이미 연결돼 있어 비밀번호를 안 묻습니다.

### ★★ 안 건드린 것과 그 이유

**정책이 쓰는 함수**(`my_org_id` `is_partner_org` `can_access_order` …)는
익명 권한을 그대로 둡니다. 거두면 지금 조용히 **0줄**이 나오던 자리가
'함수 실행 권한 없음' **오류**로 바뀝니다. 막히는 것은 같은데 화면이
깨지고, 있는지 없는지도 알려 주게 됩니다. 0줄이 더 낫습니다.

**트리거 함수**도 그대로. 홈페이지 문의는 로그인 없이 들어오는데
그 표에도 트리거가 붙습니다. **약관·처리방침**도 그대로 — /terms ·
/privacy 는 로그인 없이 보는 화면입니다.

### 시험하다 제가 낸 헛발

익명으로 문의를 넣어 보니 `new row violates row-level security policy`
가 났습니다. 순간 제가 깬 줄 알았는데, **제 시험이
`Prefer: return=representation` 을 붙였기 때문**이었습니다 —
넣은 줄을 돌려 달라는 뜻이고, 익명은 읽기 정책이 없습니다.
화면(`submitContact`)은 안 붙입니다. 붙이지 않고 다시 하니 201.

★ 익명 쪽을 시험할 때는 **화면이 하는 것과 똑같이** 해야 합니다.
  안 그러면 없는 고장을 잡으러 갑니다.


## ★★ 아홉 번째 — 문 셋이 서로 다른 규칙을 들고 있었습니다 (2026-08-21)

사장님: "주문수정했는데 파일 안 올라가네." **파일은 올라가 있었습니다.**
저장소를 열어 보니 네 개 다 있었고 크기까지 표와 같았습니다.
못 올린 것이 아니라 **'다 올렸다' 를 적는 데서 막힌 것**입니다.

`order_files` 의 update 정책이 상태를 `접수·재스캔·디자인` 으로 묶어
두었는데, **디자인센터는 단계를 안 가리고** 수정할 수 있습니다.
그래서 배송 상태 주문에 파일을 더 올리면:

| 문 | 상태를 보나 | 결과 |
|---|---|---|
| 줄 만들기 (`order_file_insert`) | 안 봄 | 통과 |
| 저장소 (`can_write_order_file`) | 안 봄 | 통과 |
| `uploaded` 로 적기 (`order_file_update`) | **봄** | **막힘** |

★★ **더 나빴던 것 — 아무도 몰랐습니다.**
  RLS 가 막으면 오류가 아니라 **0줄 고침**입니다. supabase-js 는 그것을
  성공으로 돌려줍니다(`error: null`). 그래서 화면은 "다 올렸습니다",
  표에는 pending, 주문상세는 "안 올라감" — **셋이 서로 다른 말**을 했습니다.

  ★ `.update()` 뒤에 오류만 보고 성공이라 여기지 마세요. 정책이 막는
    자리라면 **몇 줄이 고쳐졌는지**를 봐야 합니다.

**고친 법** — `mark_order_file_status(file_id, status)`.
그 칸만 · `uploaded`/`failed` 로만 · `pending` 인 줄만 ·
**올리기와 같은 문지기**(`can_write_order_file`)로. 막히면 예외를 던집니다.
일반 update 정책은 그대로 뒀습니다(이름 고치기 등은 여전히 세 상태에서만).

★ 마이그레이션이 통과한 것과 **함수가 도는 것은 다른 일**입니다.
  `upload_status` 가 열거형인데 글자를 넣어 42804 로 터졌습니다 —
  push 는 성공했고, 진짜 계정으로 불러 보고서야 알았습니다.
  이미 운영에 돌아간 파일은 몰래 안 고치고 다음 마이그레이션으로
  바로잡았습니다(무엇이 돌았는지가 남아야 합니다).

★ **짐작 하나를 버렸습니다.** `revalidatePath('/design/orders','layout')`
  가 수정 화면을 다시 그려서 올리던 것이 죽는 줄 알았는데, 그 상황만
  떼어내 재현해 보니(`/playground/revalidate`) 컴포넌트가 멀쩡히
  살아서 끝까지 갔습니다. 고칠 뻔한 곳이 엉뚱한 데였습니다.
