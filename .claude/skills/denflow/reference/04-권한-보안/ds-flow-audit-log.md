**2026-08-12 구현** (설계서 §3.5). 사용자가 법률 위반 여부를 물었고,
그 답으로 가장 먼저 만든 것입니다.

## 무엇을 남기나

환자 이름이 **화면 밖으로 나가는 순간**만 — 주문 상세 · 주문 목록 ·
배송조회 · 환자 검색 · 파일 내려받기. 클릭 하나하나를 남기면 아무도 안 봅니다.

**화면이 아니라 저장소(repository)에서** 남깁니다. 화면은 여럿인데 데이터가
나가는 문은 하나입니다. 화면마다 붙이면 언젠가 하나를 빠뜨립니다.

## ★ 5분 창으로 묶습니다 — 안 하면 기록이 거짓말을 합니다

붙이자마자 **3분에 155줄**이 쌓였는데 **대상은 2건**이었습니다.
서버 컴포넌트는 화면을 다시 그릴 때마다 다시 실행됩니다 —
파일 저장(HMR) · 링크 미리 읽기 · 뒤로가기 전부.

*"이 직원이 환자 기록을 155번 들여다봤다"* 로 읽히는 기록은
쓸모없는 정도가 아니라 **거짓말**입니다.

판단은 **DB 함수**(`record_access`)에 뒀습니다 — 서버에서 '읽고 나서 쓰면'
두 요청이 겹칠 때 둘 다 씁니다. 열쇠는 (사람 · 동작 · 대상 · **맥락**) 이라
주문목록·배송조회·검색이 따로 셉니다.

## 기록 자체가 개인정보가 되면 안 됩니다

- **환자 이름을 안 담습니다.** 무엇을 봤는지는 주문번호로만
- **검색어를 안 담습니다.** 검색어가 곧 이름입니다 — `1자 검색 · 4명` 만
- 목록은 `subject_count` 로 몇 명분인지 셉니다 (0명이면 아예 안 남깁니다)

## 고칠 수도 지울 수도 없습니다

`update`·`delete` 정책을 **안 만들었습니다**. 확인: 두 시도 모두 0줄.
남의 조직 기록도 0줄. 관리자(owner·admin)만 봅니다 —
누가 누구를 들여다봤는지가 보이는 자료입니다.
파기 배치는 나중에 service_role 로 돕니다.

## 환자 검색을 서버로 옮긴 이유

브라우저가 Supabase 에 **직접** 묻고 있었습니다. 이름 몇 글자로 명단을
훑을 수 있는 가장 민감한 조회인데 기록에 안 남았습니다.
→ `actions/patient.ts` 의 `searchPatients`.

## 남은 개인정보 항목 (2026-08-12 조사)

저는 변호사가 아니고 법률 판단은 못 합니다. 조사한 사실만:

- 저장: 환자 이름·차트번호·**생년월일**(8명 중 3명). 주민번호·연락처는 안 받음
- **파일명 13/18 개에 한글 이름** (`2026-08-11-박나래-26.obj`).
  저장소 경로는 이름을 뗐지만 표시용 `file_name` 은 원본 그대로 →
  기공소가 내려받으면 그 이름으로 저장됨.
  막았다가 사용자 요청으로 되돌렸습니다 ([[ds-flow-file-name-mask]])
- 동의·처리방침 화면 **0건** (가입 화면조차 없음)
- 보관기간·파기 규칙 **없음** (`deleted_at` 으로 가리기만)
- 이름 + 치식 + 보철 = **건강정보(민감정보)** 로 판단되면 암호화·접속기록이
  법정 요구가 됩니다 → 자문 필요
- 의료기기법: 주문·물류·정산만 하므로 지금은 거리가 있음.
  **CAD 자동설계·마진 검출·교합 분석을 붙이면 그때 다시 봐야 합니다**

  보여 준다는 약속이 아닙니다.**

★ **기록 자체는 그대로 돕니다.** `record_access` 도, 보관기간의

  (`/{sector}/account/audit`)도 주소로는 열립니다.
  없앤 것은 **계정정보에서 보러 가는 길**뿐입니다.

★ 그러므로 처리방침과 어긋나지 않습니다. 만약 사용자가 *기록을
  남기는 것 자체*를 그만두라고 하면 그때는 **처리방침을 같이
  고쳐야 합니다** — 그건 별개의 결정입니다 ([[ds-flow-privacy-policy]]).

## ★ 하루 동안 한 줄도 안 남았습니다 (2026-08-13 발견)

주문목록의 자동 갱신을 확인하다가 서버 로그에서 찾았습니다.

    [audit] 열람 기록을 남기지 못했습니다 order.list
    Route /design/orders used `cookies()` inside `after()` while rendering.

`recordAccess` 가 `after()` **안에서** getSession → createClient 를
불렀습니다. Next 는 그리는 도중에 건 after 안에서 `cookies()` 를 막습니다.
**모든 열람 기록이 실패**했고, DB 로 확인한 마지막 기록이 **하루 전**
이었습니다.

★ **화면에는 아무 표시가 없었습니다.** 실패를 삼키고 로그에만 적도록
  해 둔 판단 자체는 맞습니다 — 기록 실패가 화면을 막으면 안 됩니다.
  대신 **아무도 몰랐습니다.**

고친 방법: 쿠키를 **그리는 중에, after 밖에서** 읽고 값만 넘깁니다.
응답을 먼저 보내고 기록은 뒤에 한다는 뜻은 그대로입니다.

★ **이 고장은 화면에 아무 표시가 없는 종류입니다.** 처리방침에 "남긴다"
  고 적어 두었으니, 기록이 멎으면 알아채는 장치가 따로 있어야 합니다.
  지금은 서버 로그뿐입니다.
