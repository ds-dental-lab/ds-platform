# Den Flow 개인정보 처리현황

> **이 문서의 쓰임** — 개인정보 처리방침·동의 문구·위탁계약서를 작성하기 위한 **사실 자료**입니다.
> 법률 문서가 아닙니다. 이 문서는 "우리 시스템이 실제로 무엇을 하는가"만 적습니다.
> 무엇을 써야 하는지는 자문을 받아 정하십시오.
>
> 작성 2026-08-12 · 근거는 실제 스키마·RLS 정책·코드입니다 (추정 아님)
> 시스템: Den Flow (치과 보철 주문 플랫폼)

---

## 0. 가장 먼저 정해야 할 것 — 우리는 어느 쪽인가

환자는 자기 정보를 **치과**에 줍니다. 디자인센터·기공소는 보철을 만들기 위해
그 정보를 **넘겨받습니다.**

| 만약 디자인센터가 | 필요한 것 |
|---|---|
| **수탁자** (치과의 업무를 위탁받아 처리) | 치과와의 **위탁계약서**(법정 필수 조항), 각 치과 처리방침에 수탁자로 명시 |
| **개인정보처리자** | 자체 처리방침 + 환자 동의 |

**이것이 정해지기 전에는 동의 문구를 쓸 수 없습니다.** 환자에게 직접 동의를 받는
구조가 아니라면 동의 문구 자체가 필요 없고, 대신 위탁계약서가 없는 것이 문제가 됩니다.

> **실무 선례 (2026-08-12 추가)** — 구조가 거의 같은 유사 업체는 **자기를
> 개인정보처리자로 놓고 기공소를 수탁자로** 처리방침에 공개하고 있습니다.
> 정답이라는 뜻은 아니지만, 자문 때 들고 가면 논의가 빨라집니다.
> → [처리방침 참고대조](DS-Flow-처리방침-참고대조.md) 1항

아래 자료는 두 경우 모두에 쓰입니다.

---

## 1. 어떤 개인정보를 다루는가

### 1-1. 환자 (정보주체 본인은 서비스를 쓰지 않습니다)

| 항목 | 어디에 | 비고 |
|---|---|---|
| 환자 이름 | `patients.name` | 치과가 입력 |
| 차트번호 | `patients.chart_no` | 치과의 원내 번호 |
| 생년월일 | `patients.birth_date` | **선택 입력** |
| 주문 표시용 이름 | `orders.patient_label` | 주문 시점에 베껴 둔 값 |
| 치식·보철 정보 | `order_items` | 치아번호, 보철 종류·재료, 쉐이드, 임플란트 제조사·규격 |
| 스캔·디자인 파일 | `order_files` + 저장소 | **파일 이름에 환자 이름이 들어가는 경우가 많습니다** |
| 주문 메모 | `orders.notes` | 자유 입력 — 무엇이든 적힐 수 있음 |
| 주문 대화 | `order_messages.body` | 자유 입력 |

> **자문 시 확인할 것** — 치식·보철·임플란트 규격이 **건강정보(민감정보)** 에
> 해당하는지. 해당하면 별도 동의와 더 강한 안전조치(암호화 등)가 따라옵니다.
> 지금은 결론이 나지 않아 **더 안전한 쪽으로** 운영하고 있습니다.

**주민등록번호·고유식별정보는 받지 않습니다.** 결제·계좌 정보도 이 시스템에 없습니다.

### 1-2. 이용자 (치과·디자인센터·기공소 직원)

| 항목 | 어디에 |
|---|---|
| 이름, 이메일, 휴대전화 | `user_profiles` |
| 비밀번호 | Supabase Auth (해시 저장, 시스템이 원문을 갖지 않음) |
| 소속·권한 | `memberships` |

### 1-3. 사업자 정보 (개인정보 아님, 참고)

상호·사업자번호·대표자명·전화·주소·팩스·세금계산서 이메일 (`organizations`).
**대표자명은 개인 이름**이라 취급에 주의가 필요할 수 있습니다.

## 2. 누가 무엇을 보는가 (실제 DB 정책)

화면에서 감추는 것이 아니라 **데이터베이스가 막습니다** (PostgreSQL Row Level Security).
권한이 없으면 화면에 빈 값이 아니라 **행 자체가 오지 않습니다.**

### 2-1. 주문

`orders` 는 **그 주문에 관여한 세 조직만** 봅니다.

```
치과(clinic_org_id) · 디자인센터(design_org_id) · 기공소(lab_org_id)
```

- 다른 치과의 주문은 서로 **전혀** 보이지 않습니다
- 기공소는 **자기에게 배정된 주문만** 봅니다. 배정 전에는 안 보입니다

### 2-2. 환자 표 (`patients`)

| 누가 | 볼 수 있는가 |
|---|---|
| 치과 | **자기 환자만** |
| 디자인센터 | 거래 중인 치과의 환자 |
| 기공소 | **못 봅니다** (차트번호·생년월일에 접근 불가) |

**단, 기공소는 배정받은 주문의 `orders.patient_label`(환자 이름)은 봅니다.**
보철물과 환자를 맞추려면 이름이 필요하다는 현장 판단에 따른 것입니다.
→ 즉 **기공소가 보는 환자 정보 = 배정된 주문의 이름 + 치식·보철 정보 + 파일**

### 2-3. 파일

저장소 버킷 `order-files` 는 **비공개**입니다. 주소를 알아도 못 엽니다.
내려받을 때마다 서버가 권한을 확인하고 **짧은 시간만 유효한 링크**를 만들어 줍니다.

### 2-4. 금액

기공소는 치과 판매가를, 치과는 기공원가를 **볼 수 없습니다.**
같은 조직 안에서도 '사용자' 권한은 금액 화면이 열리지 않습니다.

## 3. 어디에 저장되는가

| | |
|---|---|
| 서비스 | Supabase (PostgreSQL + Storage + Auth) |
| **리전** | **`ap-northeast-2` — 서울** |
| 국외 이전 | **없습니다.** 데이터는 국내 리전에 저장됩니다 |

> 다만 Supabase 는 해외 사업자입니다. **국외 이전에 해당하는지는 자문이 필요합니다**
> (저장 위치는 국내이나 사업자가 해외인 경우의 해석).

## 4. 얼마나 보관하는가

**2026-08-12 설정** (디자인센터 기준):

| 무엇을 | 언제부터 세는가 | 기간 |
|---|---|---|
| 지운 주문·파일 | 지운 날 | **30일** |
| 열람 기록 | 기록이 남은 날 | **730일 (2년)** |
| 스캔·디자인 파일 | **주문이 완료된 날** | **420일 (14개월)** |

- 열람 기록 2년 — 접속기록 법정 최소 보관기간을 넉넉히 넘기려는 값입니다
- 파일 14개월 — **보철 보증기간 1년 + 두 달 여유**. 지우면 그 주문으로 다시 못 만듭니다
- **주문 기록 자체는 이 설정으로 지워지지 않습니다.** 완료된 주문은 계속 남습니다
  (치과기공물제작의뢰서 보존 의무와 무관하게 유지됨)

### 파기 방식

**자동으로 돌지 않습니다.** 관리자가 화면에서 **몇 건인지 확인하고 누를 때만** 지워집니다.
지울 때는 저장소의 파일 덩어리를 먼저 비우고 표를 지웁니다.
무엇을 몇 건 지웠는지는 `retention_runs` 에 남으며, **내용은 남기지 않습니다.**

## 5. 열람 기록 (접속기록)

환자 개인정보가 실제로 화면에 나간 순간마다 남깁니다.

| 남기는 것 | 남기지 않는 것 |
|---|---|
| 누가 (사용자 id) | **환자 이름** |
| 언제 | 조회한 내용 |
| 무엇을 (대상 id) | 검색어 원문 |
| 몇 명분이 나갔는지 | |

기록되는 행위: `order.view`(주문 상세), `order.list`(주문 목록),
`patient.search`(환자 검색), `file.download`(파일 내려받기)

- **로그에 이름을 담지 않습니다** — 담으면 개인정보를 한 벌 더 만드는 셈입니다
- 같은 사람이 같은 대상을 **5분 안에** 다시 열면 한 줄로 봅니다 (화면 새로고침으로 부풀지 않게)
- 열람 기록은 **각 조직의 관리자만** 봅니다
- **오늘 남은 기록은 지울 수 없습니다** (방금 남은 기록을 지우는 길을 막아 둠)

## 6. 이용자에게 열려 있는 권리 (현재 구현 상태)

| | 현재 |
|---|---|
| 열람 | 각 조직이 자기 데이터를 화면에서 봅니다 |
| 정정 | 주문·환자 정보 수정 가능 (단계별 제한 있음) |
| 삭제 | 접수·재스캔 단계에서만 주문 삭제. 그 뒤에는 기록으로 남습니다 |
| 처리정지 | **화면 없음** |
| 열람 기록 제공 | 관리자만 조회. **정보주체(환자)에게 제공하는 창구는 없음** |

> 환자는 이 서비스의 이용자가 아닙니다. 환자의 권리 행사는 **치과를 통해** 이뤄지는
> 구조입니다. 이 부분이 위탁 관계 정리와 직결됩니다.

## 7. 아직 없는 것 (솔직하게)

- **개인정보 처리방침 화면** — 라우트도 링크도 없습니다 (현재 404)
- **동의 절차·동의 문구** — 없습니다
- **민감정보 암호화** — 건강정보 결론이 나면 필요할 수 있습니다
- **파일명 마스킹** — 만들었다가 되돌렸습니다. **파일 이름에 환자 이름이 그대로 남습니다**
  (개인정보가 가장 눈에 띄게 노출되는 자리)
- **위탁계약서** — 있는지 확인 필요
- 처리정지 요구 처리 창구

## 8. 자문 때 물어보실 것 (정리)

1. **디자인센터·기공소는 수탁자인가, 처리자인가** → 위탁계약서가 필요한가
2. **치식·보철·임플란트 정보가 민감정보(건강정보)인가** → 별도 동의·암호화 여부
   - 아니라면 열람 기록을 730일에서 365일로 줄여도 됩니다
3. **접수 단계에서 삭제한 주문**이 치과기공물제작의뢰서 2년 보존 대상인가
   - 맞다면 '지운 주문' 30일 → 730일로 올려야 합니다
4. **국내 리전에 저장되지만 해외 사업자(Supabase)** 를 쓰는 것이 국외 이전인가
5. **파일 이름의 환자 이름**을 가려야 하는가
6. 기공소가 환자 실명을 보는 것이 위탁 범위 안에서 정당한가
