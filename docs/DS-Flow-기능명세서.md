# Den Flow 기능 명세서

**문서 버전** v0.4 · 2026-08-04
**작성 범위** 프로토타입(치과 계정 완성, 디자인센터 계정 진행 중) 기준

---

## 1. 개요

### 1.1 목적

Den Flow는 치과 보철물 제작 과정에서 **구강 스캔 데이터와 보철 정보를 세 주체가 주고받는 웹 플랫폼**이다. 치과가 스캔 데이터와 보철 사양을 올리면 디자인센터가 설계하고, 기공소가 제작·배송하는 흐름을 하나의 시스템에서 처리한다.

### 1.2 해결하려는 문제

기존에는 스캔 파일을 이메일·메신저·외장하드로 주고받고, 보철 사양은 전화나 종이 의뢰서로 전달했다. 이로 인해 파일 유실, 사양 오전달, 진행 상황 확인 불가, 정산 근거 부재가 반복된다.

### 1.3 전체 흐름

```
치과                디자인센터              기공소
─────              ──────────             ──────
주문 등록      →    디자인 작업       →    제작
스캔 업로드         STL 업로드              출고
     ↑                  │
     └──────────────────┘
   재스캔 요청 / 수정 요청
   (디자인센터 → 치과)
```

케이스는 한 방향으로 흐른다. 되돌리기는 **디자인센터가 치과에 요청하는 경로 하나뿐**이며, 재스캔 요청과 수정 요청 모두 디자인센터가 발행한다. 기공소는 되돌리기 권한을 갖지 않는다.

## 2. 용어 정의

| 용어 | 설명 |
|---|---|
| 케이스 / 주문 | 환자 한 명에 대한 보철 제작 의뢰 단위 |
| 치식 | 치아 번호 체계(FDI). 상악 18~28, 하악 48~38 |
| 지대치 | 보철을 씌우는 기둥 치아 |
| 폰틱 | 결손 부위를 메우는 인공치아. 화면에 **X**로 표기 |
| 브릿지 | 인접 치아가 하나로 연결된 보철물 |
| 쉐이드 | 치아 색조. Vita classic 등 색조 체계로 지정 |
| 마스터 정보 | 디자인센터가 관리하는 임플란트 제조사·타입·사이즈·스크류 목록 |
| 즐겨찾기 | 치과가 자주 쓰는 임플란트 모델을 저장해 둔 목록 |

## 3. 계정 체계

### 3.1 계정 유형

| 유형 | 역할 | 식별색 | 파일 |
|---|---|---|---|
| 치과 | 주문 등록, 스캔 업로드, 수령 확인 | 파랑 | dental-clinic-portal |
| 디자인센터 | 디자인 작업, 임플란트 마스터 관리, 기공소 배정 | 인디고 | dental-design-portal |
| 기공소 | 제작, 출고 | 브라스 | (예정) |

세 계정은 **별도 화면으로 완전히 분리**한다. 상단 배지와 사이드바 활성색으로 현재 어느 계정인지 즉시 구분된다.

**조직 간 거래 관계는 1:1 전속이다.** 한 치과는 하나의 디자인센터와만 거래하며, 사용자는 하나의 조직에만 소속된다. 다대다 거래(멀티테넌시)는 현 단계에서 다루지 않는다.

### 3.2 계정 내부 권한 (치과 기준)

| 권한 | 이용 금액 조회 | 그 외 기능 |
|---|---|---|
| 대표 / 관리자 | 가능 | 전체 사용 |
| 직원 | **불가 (블라인드)** | 전체 사용 |

직원 계정은 HOME의 이용 금액이 가려지고 정산 바로가기가 숨겨진다. 그 외 주문 등록·조회·배송 확인은 동일하게 사용한다.

> **보안 주의** — 현재 블라인드는 화면 단에서만 가린다. 실서비스에서는 서버가 직원 계정 요청에 금액 필드를 아예 내려주지 않아야 한다.

### 3.3 섹터 간 정보 차단

| 정보 | 치과 | 디자인센터 | 기공소 |
|---|---|---|---|
| 기공소명 | **숨김** | 표시 | 표시 |
| 기공수가 / 기공원가 | **숨김** | 표시 | 표시 |
| 담당 디자이너 | 숨김 | 표시 | 표시 |

치과는 기공소를 지정하지 않는다. 디자인센터가 회원가입된 기공소 중에서 배정한다. 화면 노출은 `PORTAL.showLab` 설정값 하나로 제어한다.

## 4. 치과 계정 기능

### 4.1 HOME

| 영역 | 내용 |
|---|---|
| 이용 금액 | 이번 달 누적 청구 예정 금액 (직원 권한은 블라인드) |
| 진행중 상태 | 재스캔 · 접수 · 디자인 · 제작대기 · 제작 · 배송 건수 |
| 진행중 이슈 | 재스캔 · 리메이크 · 리페어 · 아날로그 건수 |
| 사용금액 추이 | 월별 사용액 막대그래프 |
| 오늘 배송 예정 | 요청시한이 오늘인 케이스 목록 (클릭 시 상세 이동) |
| 공지사항 | 최근 6건 (클릭 시 게시판 해당 글 열림) |

모든 수치는 실제 주문 데이터에서 계산된다.

### 4.2 주문등록

입력 순서는 **① 보철물 종류 → ② 재료 → ③ 쉐이드 → ④ 치식**으로 고정된다. 상위 항목 없이 치식을 누르면 단계별 안내가 뜨거나 해당 선택 창이 자동으로 열린다.

**4.2.1 환자정보**

| 항목 | 규칙 |
|---|---|
| 이름 | 필수. 이름 또는 차트번호 |
| 요청시한 | 기본값 +7일 |
| 주문유형 | 모델리스 / 모델 포함 / 모델만 / 리페어 (리메이크는 §4.10 참조) |
| 치과 | **계정 치과명 자동 입력, 수정 불가** |

**4.2.2 보철선택**

| 종류 | 재료 | 표기 |
|---|---|---|
| 크라운 (Cr) | 지르코니아 | Zir-Cr |
| | PMMA | Pmma-Cr |
| 인레이 (In) | 하이브리드 | Hy-In |
| | 지르코니아 | Zir-In |
| 임플란트 | Abut+Zir(SCRP) | Abut+Zir(SCRP) |
| | Abut + Zir(Cementation) | Abut + Zir(Cementation) |
| | Abut + PMMA | Abut + PMMA |
| | 커스텀 어버트먼트 | Custom Abutment |

- 재료는 종류에 종속된다. 종류를 바꾸면 재료·모델 선택이 초기화된다.
- 임플란트는 `재료-종류` 약칭 대신 재료 표기를 그대로 쓴다.

**4.2.3 쉐이드**

- 체계: Vita classic / Vita 3D Master / Ivoclar
- 첫 클릭 → 치아 전체(치경부·절단부)에 적용
- 이후 색조 클릭 → 그 색조만 활성(파란색)되고 대기 상태
- 치아 그림의 위(치경부) 또는 아래(절단부) 클릭 → 해당 부위만 적용
- 활성 표시는 **항상 마지막에 누른 색조 하나에만** 켜진다
- 쉐이드 미지정 상태로 치아를 누르면 쉐이드 창이 자동으로 열리고, 확인하면 그 치아에 바로 적용된다

**4.2.4 임플란트 모델 (임플란트 선택 시 필수)**

- 디자인센터가 등록한 마스터에서 **제조사 → 타입 → 사이즈 · 스크류 · 옵션** 순으로 선택
- 타입은 제조사에, 사이즈·스크류·옵션은 타입에 종속
- 등록한 모델은 즐겨찾기 칩으로 저장되어 이후 클릭 한 번으로 선택
- 즐겨찾기가 비어 있는 상태에서 치아를 누르면 등록 창이 자동으로 열린다
- 모델 없이는 치식에 등록되지 않는다

**4.2.5 치식선택**

- 상악 18~28 / 하악 48~38, 치종별로 다른 외곽선 (대구치·지치·소구치·견치·중절치·측절치)
- 선택한 치아는 보철 종류 색으로 채워지고, 같은 조건으로 다시 누르면 해제
- **PMMA · 폰틱 토글**로 속성 부여. 폰틱은 번호 대신 **X** 표기
- 하단 요약 카드에 `Zir-Cr | 42, X, 31 (A3)` 형태로 정리
- 초기화 버튼은 선택 항목이 하나라도 있으면 빨간색으로 강조되며, 누르면 확인창을 거친다

**4.2.6 인접치 연결 (브릿지)**

| 조건 | 연결 | 해제 |
|---|---|---|
| 인접 + 같은 종류 + 같은 재료 (크라운·임플란트) | 자동 | − 버튼으로 가능 |
| 한쪽이라도 폰틱 | 무조건 | 불가 (고정) |
| 사이 치아가 비어 있음 | 안 됨 | — |
| 인레이 | 안 됨 | — |

연결된 치아는 하나의 박스로 묶이고, 박스 위 − 버튼으로 끊거나 + 버튼으로 다시 붙인다.

**4.2.7 한 치아 중복 등록**

허용 조합은 아래 셋뿐이며, 그 외 조합은 기존 항목을 덮어쓴다.

| 조합 |
|---|
| 크라운 지르코니아 + 크라운 PMMA |
| 임플란트 Abut+Zir(SCRP) + Abut + PMMA |
| 임플란트 Abut + Zir(Cementation) + Abut + PMMA |

중복 등록된 치아에는 **2** 배지가 붙고, 요약에는 두 줄로 분리 표시된다.

**4.2.8 제작옵션**

- 항목: 훅, 폰틱타입
- 별 버튼으로 현재 값 조합을 즐겨찾기 저장 → `기본 옵션` 옆에 칩으로 추가
- 칩 클릭 시 해당 값 적용, ✕로 삭제

**4.2.9 스캔/쉐이드 파일**

- 지원 형식: PLY · OBJ · STL · DXD · ZIP · PNG · JPG
- 드래그 앤 드롭 또는 클릭 업로드, 개별 삭제 가능
- 최소 1개 이상 필수

**4.2.10 주문완료**

환자명·치식·파일을 검사한 뒤 주문번호(`ORD-YYMMDD-###`)를 발급하고 상태 `접수`로 저장한다. 등록 즉시 주문목록·배송조회·정산·HOME에 반영된다.

### 4.3 주문목록

**검색 조건** — 기간(3개월/6개월/1년/전체), 치과명, 환자명

**상태 필터** — 아이콘 + 건수 배지. 담당 섹터별로 색을 통일한다.

| 섹터 | 상태 | 색 |
|---|---|---|
| 치과 | 재스캔 · 접수 | 주황 |
| 디자인센터 | 디자인 | 자주 |
| 기공소 | 제작대기 · 제작 · 배송 | 파랑 |
| — | 완료 | 회색 |

**이슈 필터** — 재스캔 · 리메이크 · 리페어 · 아날로그

**표 항목** — 주문상태 · D-Day · 접수일 · 치과 · 환자명 · 치식 · 이슈 · 리메이크 횟수
(기공소 열은 치과 계정에서 숨김. 모든 열 정렬 가능, 페이지당 10건)

### 4.4 주문 상세

| 영역 | 내용 |
|---|---|
| 상단 | 상태 · 치과 · 환자명 · 요청시한 · D-Day · 기공의뢰서 |
| 치식도 | 읽기 전용. 보철 종류 색으로 표시, 폰틱은 X |
| 제작보철 | `Zir-Cr / 45, 44 (A2/A3)` 형태, 브릿지는 한 줄로 묶임 |
| 제작옵션 | 훅 · 폰틱타입 |
| 기타 요청사항 | 치과가 입력한 요청 |
| 스캔/쉐이드 파일 | File Count 표시, 개별 삭제·전체 내려받기 |
| 디자인 파일 | 디자인센터가 업로드한 STL |
| 메모 | 200자 제한, 작성자·시각과 함께 누적 (우측 패널) |

**하단 액션 (치과)** — 주문 삭제 · 주문 수정 · 주문목록

수정·삭제는 **접수 및 재스캔 상태에서만** 가능하다. 디자인 단계로 넘어가면 버튼이 잠기고 사유가 표시된다. 주문 수정을 누르면 주문등록 화면에 기존 값이 모두 불려오고, 저장 시 새 주문이 생기지 않고 기존 주문이 갱신된다.

### 4.5 배송조회

- 월~토 6열 주간 보드, 요청시한 기준으로 카드 배치
- 오늘 열은 강조 표시
- 카드: 환자명 · 치과명 · 주문번호 · 주문일 · 이슈 태그
- 주 단위 이동, 검색(치과/기공소 대상 선택)

### 4.6 정산

**이용내역 탭**
- 주문 금액 · 조정 금액 · 총 합계
- 하위 탭: 보철 세부내역 / 보철 조정 내역
- 표: 요청시한 · 환자명 · 타입 · 치식 · 기공료 · 리메이크 횟수
- EXCEL 내려받기 (CSV, 한글 인코딩 처리)

**청구서 탭**
- 조회 기간(월), 상태 필터(미입금/완료), 전체 검색
- 표: 청구 번호 · 발행일 · 청구 방법 · 청구 대상 · 청구 금액 · 미납 금액 · 상태 · 납부기한

### 4.7 사용자

- 표: 이름 · 계정권한 · 휴대전화 · 이메일
- 사용자 등록: 계정권한(직원/대표/관리자) · 이메일 · 이름 · 휴대전화(국가번호 포함)
- 이메일 형식·중복 검사, 기존 사용자 수정·삭제

### 4.8 게시판

- 공지사항 (No. · 제목 · 공지 기간 · 작성자 · 작성일)
- FAQ (No. · 분류 · 제목 · 작성일)
- Q&A (No. · 제목 · 작성자 · 상태 · 작성일)
- 검색, 페이지네이션, 본문 팝업

### 4.9 계정 설정

우측 상단 계정 아이콘 → 드롭다운 → 계정 정보 / 알림 설정 / 비밀번호 변경 / 계정 전환 / 로그아웃

| 탭 | 항목 |
|---|---|
| 계정 정보 | 사업자 정보(상호·사업자등록번호·대표전화·주소), 내 정보(이메일·이름·휴대전화) |
| 결제 관리 | 청구서 수령 방식(전체/이메일/팩스), 청구서·세금계산서 수신 이메일, 팩스, 정산 기준일(1일/26일) |
| 알림 설정 | 알림 수신여부 마스터 토글 + 카카오알림톡 · 푸시 · 이메일 |
| 비밀번호 변경 | 현재/신규/확인, 적합성 게이지 |

### 4.10 리메이크

완성된 보철물에 문제가 있을 때 치과가 재제작을 요청하는 절차다.

**신청 조건**

| 항목 | 규칙 |
|---|---|
| 신청 주체 | **치과 계정만** |
| 신청 가능 상태 | **배송 · 완료** 상태의 주문만. 그 외 상태에서는 버튼이 비활성 |
| 진입 위치 | 주문 상세 하단 |

**동작**

리메이크를 신청하면 기존 주문을 수정하지 않고 **새 주문이 생성된다.**

1. 원주문의 환자 · 치식 · 보철 사양 · 옵션을 그대로 복사한다
2. 새 주문에 **리메이크 태그**가 붙는다
3. 원주문을 참조 관계로 연결한다
4. 상태 `접수`로 진입한다
5. 이후 접수 → 디자인 → 제작대기 → 제작 → 배송 → 완료까지 **일반 주문과 완전히 같은 흐름**을 탄다

**스캔 데이터 처리**

리메이크 신청 화면에는 두 가지 수단을 함께 제공한다.

| 수단 | 설명 |
|---|---|
| 이전 스캔 데이터 그대로 사용 | 체크박스. 켜면 원주문의 스캔 파일을 새 주문에 연결한다 |
| 새 스캔 업로드 | 업로드 영역. 새로 촬영한 파일을 올린다 |

둘을 함께 쓸 수도 있다(이전 데이터 + 추가 촬영본).

**진행 차단 규칙** — 체크박스도 꺼져 있고 새로 올린 파일도 없으면 **스캔 데이터가 없는 상태**이므로 리메이크를 진행할 수 없다. 신청 버튼이 비활성화되고 안내가 표시된다.

원주문은 `완료` 상태로 남고 이력이 보존된다. 원주문의 리메이크 횟수는 1 증가한다.

**정산**

리메이크 태그가 붙은 주문은 **청구 금액에서 제외한다.** 무상 재제작이므로 이용내역에는 표시하되 금액은 0으로 기록한다.

**표시**

| 화면 | 표시 |
|---|---|
| 주문목록 | 이슈 열에 `리메이크` 태그 |
| 주문상세 | 상단에 리메이크 표시 + 원주문 바로가기 |
| 정산 이용내역 | 행은 표시, 기공료 0 |

### 4.11 리페어

완성된 보철물의 일부를 수리하는 절차다. 리메이크와 달리 **디자인 작업을 거치지 않는다.**

**신청 조건**

| 항목 | 규칙 |
|---|---|
| 신청 주체 | 치과 계정 |
| 신청 가능 상태 | 배송 · 완료 상태의 주문 |
| 진입 위치 | 주문 상세 하단 |

**동작**

1. 원주문의 환자 · 치식 · 보철 사양을 복사한 새 주문을 만든다
2. **리페어 태그**가 붙는다
3. 상태가 `접수`가 아니라 **`제작대기`로 바로 진입**한다 — 디자인센터를 거치지 않는다
4. 원주문을 담당했던 **기공소에 배정되고 알림이 발송된다**
5. 이후 제작대기 → 제작 → 배송 → 완료까지 일반 주문과 같은 흐름을 탄다

**정산** — 리메이크와 동일하게 **청구 금액에서 제외한다.**

**리메이크와의 차이**

| 항목 | 리메이크 | 리페어 |
|---|---|---|
| 진입 상태 | 접수 | **제작대기** |
| 디자인센터 | 거침 | **거치지 않음** |
| 기공소 배정 | 디자인센터가 수행 | **원주문 기공소로 자동 배정** |
| 알림 | 디자인센터 | **기공소** |
| 스캔 데이터 | 재사용 또는 신규 업로드 필수 | 원주문 정보 승계 |
| 과금 | 없음 | 없음 |

## 5. 디자인센터 계정 기능

치과 계정과 화면 구성은 동일하되, **모든 치과의 데이터를 대상으로 한다**는 점과 아래 기능이 추가된다.

### 5.1 HOME (치과와 다른 부분)

| 영역 | 내용 |
|---|---|
| 진행중 상태 | 재스캔 · 접수 · 디자인 · 제작대기 · 제작 · 배송 |
| 작업 리스트 | 치과명 · 환자정보 · 디자이너 · 상태 |

### 5.2 임플란트 (디자인센터 전용)

**5.2.1 마스터 관리**

5열 구조 — 제조사 / 타입 / 사이즈 / 스크류 / 옵션

- 각 항목은 **이름 + 코드**로 구성되며 `more`로 수정·삭제
- 종속 관계: 제조사를 선택해야 타입 추가 가능, 타입을 선택해야 사이즈·스크류·옵션 추가 가능
- 상위 삭제 시 하위 전체 삭제 (확인창에서 고지)
- 여기서 저장한 내용이 **치과 계정의 임플란트 모델 등록 창에 그대로 반영**된다

> 임플란트 종류가 많아 한 번에 입력할 수 없으므로, 신규 정보가 생길 때마다 디자인센터가 추가하고 치과는 그것을 골라 쓰는 구조로 운영한다.

**5.2.2 치과 자주쓰는 임플란트 (강제 배포)**

- 치과를 선택하면 해당 치과의 즐겨찾기 목록 표시
- `임플란트 배포` → 마스터에서 모델 선택 → 치과 목록에 직접 추가
- 각 항목에 **디자인센터 배포 / 치과 등록** 배지로 출처 구분
- 회수 기능 제공

### 5.3 배송조회

해당 치과가 아닌 **모든 치과의 배송 정보**를 표시한다.

### 5.4 추가 예정 기능

- 케이스 접수 → 디자인 시작 → STL 업로드 → 디자인 완료
- 재스캔 요청 (치과로 반려)
- **기공소 배정** — 회원가입된 기공소 중에서 선택
- 디자이너 배정 및 작업량 관리
- **기공수가 단가표 관리** — 치과별 · 보철물 종류별 · 치식별로 금액을 다르게 설정 (§6.1)

## 7. 상태 전이

### 7.1 상태 목록

| 상태 | 담당 섹터 | 다음 단계 |
|---|---|---|
| 접수 | 디자인센터 | 디자인 |
| 재스캔 | 치과 | 접수 |
| 디자인 | 디자인센터 | 제작대기 |
| 제작대기 | 기공소 | 제작 |
| 제작 | 기공소 | 배송 |
| 배송 | 치과 | 완료 |
| 완료 | — | 종료 |

> **디자인 컨펌 상태는 보류한다.** 향후 업데이트 예정 기능이므로 현재는 모든 화면에서 표시하지 않는다. 데이터 모델에는 예약해 두되 사용하지 않는다.

### 7.2 되돌리기

되돌리기는 **디자인센터가 치과에 요청하는 경로만** 존재한다.

| 동작 | 방향 | 결과 |
|---|---|---|
| 재스캔 요청 | 디자인센터 → 치과 | 상태 `재스캔`, 이슈 `재스캔`. 스캔 데이터 재촬영 요청 |
| 수정 요청 | 디자인센터 → 치과 | 상태 `재스캔`, 이슈 기록. 보철 사양·요청사항 확인 요청 |
| 리메이크 | 치과 → (신규 주문) | **배송 · 완료 상태에서만 신청 가능.** 신규 주문이 `접수` 상태로 생성되고 리메이크 태그가 붙는다. 스캔 데이터 재사용 또는 신규 업로드 필수. 청구 제외 (§4.10) |
| 리페어 | 치과 → (신규 주문) | **배송 · 완료 상태에서만 신청 가능.** 신규 주문이 **`제작대기`** 로 진입해 원주문 기공소에 배정되고 알림 발송. 청구 제외 (§4.11) |

기공소는 상태를 앞으로 진행시킬 수만 있고 되돌릴 수 없다.

### 7.3 수정 가능 시점

주문 수정·삭제는 **접수 및 재스캔 상태에서만** 가능하다. 디자인이 시작되면 잠긴다.

teeth[]       { n, type, material, shade{system,cervical,incisal},
                model, pmma, pontic }
bridges[][]   연결된 치식 묶음
options{}     제작옵션 (훅, 폰틱타입)
notes         기타 요청사항

환자 실명은 치과와의 소통을 위해 저장한다. 다만 저장 위치를 주문에서 분리하고 접근 권한을 별도로 통제하며, 기공소에는 마스킹된 값만 노출한다. 인증·규제 요건이 확정되면 재검토한다.

한 치아에 보철이 둘일 수 있으므로 `teeth`에는 같은 번호가 두 번 들어갈 수 있다.

## 10. 기술 현황과 과제

### 10.1 현재 구조

브라우저에서 단독 실행되는 HTML 프로토타입이다. 데이터는 브라우저 저장소에 보관된다.

### 10.2 제약 사항

| 항목 | 현재 | 필요 |
|---|---|---|
| 파일 용량 | 3MB 초과 시 세션 한정 | 실제 STL은 10~50MB. 오브젝트 스토리지 필요 |
| 계정 인증 | 없음 (화면 전환만) | 로그인·세션·권한 검증 |
| 권한 차단 | 화면 단 블라인드 | 서버가 필드 자체를 미전송 |
| 동시 편집 | 마지막 저장 우선 | 충돌 처리 |

### 10.3 서버 전환 계획

| 조각 | 후보 | 역할 |
|---|---|---|
| 웹 호스팅 | Vercel | 화면 배포 |
| 데이터베이스 | Supabase (서울 리전) | 주문·사용자·마스터 |
| 파일 스토리지 | Supabase Storage | 스캔·디자인 파일 (presigned URL 직접 업로드) |
| 인증 | Supabase Auth | 계정 유형별 권한, Row Level Security |

### 10.4 개인정보 관련

환자 이름과 차트번호를 다루므로 국내 개인정보보호법상 처리방침·암호화·위탁계약 의무가 따른다. 서버 리전을 국내로 지정해 국외 이전 문제는 피할 수 있다.

**현재 방침** — 치과와의 소통을 위해 환자 실명을 저장한다. 대신 아래 조치로 위험을 낮춘다.

- 환자 정보를 주문 테이블에서 분리해 별도 접근 권한으로 통제
- 기공소 화면에는 마스킹된 값만 노출 (기공소는 치식과 보철 사양만 있으면 된다)
- 저장 시 암호화, 열람 시 감사 로그 기록

인증 취득이나 규제 요건이 확정되면 실명 미저장 방식으로 전환할 수 있도록 구조를 열어 둔다.

> 의료 데이터는 판단이 갈리는 영역이므로 사업화 전 전문가 확인을 권한다. 본 문서는 법률 자문이 아니다.

## 부록 A. 확정 필요 항목

### 확정된 항목 (v0.3)

| 항목 | 결정 |
|---|---|
| 기공수가 단가표 주체 | **디자인센터 계정**이 설정. 치과별로 다른 금액 적용 |
| 단가 구분 기준 | 보철물 종류 · 치식별. 세부 구성은 화면 시안 확인 후 확정 |
| 리메이크 절차 | 치과가 배송 · 완료 상태에서만 신청. 리메이크 태그를 단 신규 주문이 `접수`로 진입, 이후 동일 흐름. 청구 금액 제외 |
| 임시치아 상태 | **기능 삭제.** 진행중 임시치아 카드 제거 |
| 디자인 컨펌 단계 | **보류.** 향후 도입 시 재정의 |
| 리메이크 스캔 데이터 | 이전 데이터 재사용 체크박스 + 신규 업로드 둘 다 제공. 둘 다 비어 있으면 진행 차단 |
| 리페어 절차 | 청구 제외. `제작대기`로 바로 진입해 원주문 기공소 배정 + 알림. 이후 동일 흐름 |
| 단가표 치식 구분 | **전치 / 구치** 두 갈래 |
